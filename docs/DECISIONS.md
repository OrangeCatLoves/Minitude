## Phase 2 choices (not yet confirmed by you)

| # | Choice | Where |
| --- | --- | --- |
| 21 | **SQLite** (`better-sqlite3`, version 12 so Node 20 still works) in one file, `packages/server/data/minitude.db`, seeded from the seed JSON on the very first start. Postgres later behind the same `Repo` methods. You chose "SQLite first" to avoid a monthly cost. | `db/` |
| 22 | The tier belongs to the **canonical answer**. Typos and other names are stored as "spellings" pointing at it, so every way of writing an answer scores the same, and a model that re-scores an answer we already have is overruled by the stored tier. | `judge/pipeline.ts` |
| 23 | Only a **sure** "does not count" is stored forever; "not sure" answers are never stored or counted (the player may retry). A "medium" valid answer is counted but flagged for a person (`answers review`). | `judge/pipeline.ts` |
| 24 | With a model configured, a near-miss spelling goes to the model rather than being guessed locally ("Cesium" must not become "Cerium"). Without a model (mock mode) one unambiguous typo is still forgiven. | `judge/pipeline.ts` |
| 25 | A "same as" match that looks nothing like the typed text is used once but not remembered. | `close()` in `pipeline.ts` |
| 26 | Rarity comes from the model's **own judgement** against example answers at temperature 0. No web search yet (decide after the trial). | `judge/prompt.ts` |
| 27 | Model budget defaults: 10 calls a minute, 200 a day, counted from the database log. Over budget the call is refused, not sent; players see "busy". The command line waits out the minute instead. | `llm/guard.ts` |
| 28 | Server clock: 30 s + 0.55 s start delay + 3 s grace + time the server spent checking; questions start in order; at most 12 tries per question. | `app.ts` |
| 29 | ~~Prompts are sent to the browser when a run starts.~~ **Phase 3: a prompt is sent only when its question starts** (the reply to `/start`), for solo runs too. | `app.ts` |
| 30 | The model writes questions as **drafts**; nothing is played until a person approves it. A second "audit" call drops broken answers and flags doubtful ones; thresholds in `generate/generate.ts`. | `generate/` |
| 31 | The seed bank is not enlarged by hand; the 22-question target is reached by running the generator and approving results. | |
| 32 | Corrections (`answers set-tier`, `remove`) affect future answers only; runs already played keep their points. Each one is logged. | `db/repo.ts`, `changes` |
| 33 | No admin web page or admin API: the review tools are a command line (`npm run cli -- help`). | `cli/` |
| 34 | `.env` files (`packages/server/.env` or the repo root) are read at start-up; real environment variables win. | `env.ts` |
| 35 | Every typed answer is kept in `attempts` (text only) for disputes and analysis. | `db/schema.ts` |

## Phase 3 choices (the first four are yours; the rest are not yet confirmed by you)

| # | Choice | Where |
| --- | --- | --- |
| 36 | **You decided:** the Daily resets at **midnight UTC** (08:00 Singapore), the same for everyone. | `core/daily.ts` |
| 37 | **You decided:** **guests only**, tracked by the browser, no sign-up. | `web/api.ts` |
| 38 | Guest = a random id kept in this browser's storage. Clearing storage, a private window or another browser means a new guest and a second attempt. A limit of **10 daily runs per network per day** (hashed, not readable, changes daily; 0 turns it off) blunts repeated clearing but also means ten people behind one office address share the cap. | `app.ts`, `clientip.ts`, `DAILY_PER_IP` |
| 39 | **You decided:** the questions are **mixed categories**: at most one per category in a day, the ones used longest ago first, the rest filled from the other questions when there are fewer than 7 categories. | `server/src/daily.ts` |
| 40 | **You decided (after my advice):** host on **Fly.io**, one small machine in Singapore, one 1 GB disk, SQLite on the disk. | `Dockerfile`, `fly.toml`, `docs/DEPLOY.md` |
| 41 | The day's seven questions are **chosen once and stored** (first request of the day, or the hourly job that also prepares tomorrow). Approving or rejecting questions later never changes a day that exists. | `daily_sets` |
| 42 | **One attempt, and closing the page ends it.** A closed or reloaded page scores the unanswered questions 0 (sent as the page closes); a run silent for 2 minutes is closed the same way. The title says so: "ONE ATTEMPT A DAY. CLOSING THE PAGE ENDS YOUR RUN." Harsh, but without it a reload is a free second try. | `abandon`, `STALE_RUN_MS` |
| 43 | Daily numbering: "DAILY #1" is the first day that has a stored set; then +1 per UTC day. | `meta.daily_epoch` |
| 44 | Standings are anonymous: players, your rank, how many are below you, the best total. "You beat N%" shows only with **10 or more players**, so early on it cannot say "100%" about two people. | `core/daily.ts` |
| 45 | Streak = consecutive UTC days with a finished daily; it stays alive through today until the day ends. It is counted by the server from the guest id, so clearing the browser's storage also resets the streak. | `streakOf` |
| 46 | After a daily, the title shows TODAY'S RESULT (the report again, from the server) and a countdown to the next one; SOLO RUN stays available any time and does not touch the standings. | `web/game.ts` |
| 47 | The daily share text starts "MINITUDE DAILY #N" and adds the site address (not on localhost). | `core/report.ts` |
| 48 | The server keeps **7 daily copies** of the database on its disk (`BACKUP_DIR`, `BACKUP_KEEP`); Fly volume snapshots are the second layer. | `backup.ts` |
| 49 | One machine, always on, no auto-stop (SQLite is on that machine's disk; two machines would be two databases). A deploy therefore takes the site down for a moment. | `fly.toml` |
| 50 | The server runs TypeScript directly through `tsx` in the container (no compile step), one process, about 110 MB. | `Dockerfile` |
